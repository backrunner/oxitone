# 以 TypeScript 源码保存的 GPUI DAW：无显式 ID 与生成式编排编辑

已被 [完整代码 / DAW 架构](../designs/source-daw/README.md) 取代。以下保留探索过程；
旧 ABI 兼容和只读限制不再约束目标设计，当前源码事实仍可作为迁移基线。

状态：讨论草案，2026-09-08。本文提出后续产品方案，不表示已经实现，不替代
`docs/09-preview-app.md`、`docs/11-plugin-ui.md` 当前的只读契约。

## 1. 用户约束与推荐方向

- 用户不需要为 Track、Pattern、Clip、Note 或效果器手写 ID；工具也不向源码自动塞入
  UUID、隐藏 ID 注释、装饰器或要求用户维护的绑定标记。
- 自然使用函数、循环、map/flatMap、共享 Pattern 和生成式音乐。图形编辑必须考虑
  用户移动、删除、复制、替换其中一个实例，或者只改变一次循环中的某个音符。
- 保存的音乐语义完整存在于 TS 源文件及其正常 imports 中。删除编辑器缓存，使用同样的
  SDK、依赖和素材重新执行入口，仍应得到保存的结果。素材及插件库仍是正常外部依赖。
- 保留没有被编辑的抽象和源码；不能每次保存就把整个工程打印成 snapshot 对象。

推荐采用“来源追踪 + 局部程序改写 + 按需展开”的混合方案。把可视化操作理解为一次
有作用范围的源码重构，而不是维护永远一一对应的 AST 节点与图形对象。
允许编辑打破原抽象，但只在表达该编辑所需的最小范围内打破。

逐项 API 盘点见 [生成与组合编辑审计](2026-09-08-higher-order-edit-audit.md)：当前 chord/arp、
24 个 automation 入口、Clip/Sample 派生、切片/钢琴分区与配置组合均已核对。
据此将写回分为有限集合编辑、时间函数区间编辑、配置/绑定编辑；“加局部条件”只是其中
一种输出形式。chord/arp 的单音编辑默认作用于生成结果，不自动反推根音、和弦类型或 arp 输入。

外部插件与 GPUI 插件管理器是必需范围，详见 [插件管理方案](2026-09-08-plugin-manager.md)。
通用/自定义面板、实例添加替换、参数与 automation 共用源码事务；注册来源也写入正常 TS。
当前 C ABI v1 的 resources/state/native UI 缺口须按能力显式处理，不以 wire 有字段宣称支持。

需要接受一个基本边界：在没有持久标记的情况下，两个完全相同的生成实例经过任意源码
重写、重排或删除后，不总能判断哪个是原来的实例。AST、sourcemap、内容 hash 和 AI
都不能消除这种信息缺失。应当放弃有歧义的旧选择或暂停未保存事务，不能猜测后写错对象。

## 2. 当前实现提供什么、缺少什么

- `packages/cli/src/bundle.ts` 已处理本地依赖图、source-relative 资源和 inline sourcemap。
  可在 TS 被 esbuild 擦除之前增加 AST 分析；npm external、运行期 import 和文件输入并不
  等于已获取全部源码。编辑范围限定为可访问的工程源码，包依赖保持正常调用。
- `packages/cli/src/preview/runner.ts` 已提供隔离执行、watch、snapshot revision 和结果去重；
  目前没有属性来源映射、源码草稿、编辑事务或反向命令。
- `Project.fromSnapshot` 能恢复 authoring 数据，不能恢复函数、变量、注释或闭包。
  当前 `Project.save()` 是 manifest/素材保存，不能直接视为本方案的 TS 保存。
- Pattern 不可变；PatternClip 的位置、所属 Track 和 Pattern 引用目前也是 readonly。
  移动、替换、删除和局部派生需要新增 authoring 操作或重新执行候选源码。
- wire entity ID 仍是引擎引用所必需的内部细节。现有 ID 生成依赖创建顺序，Note ID 可选，
  insert 地址依赖槽位索引；它们不能直接用作跨源码版本的编辑定位符。
- 当前概率事件依赖 `hash64(projectSeed, clipId, loopIteration, noteOrdinal)`。
  分裂循环、重建 Clip 或重排 Note 会影响听到的结果，详见第 9 节。

## 3. 三种身份必须分开

| 身份            | 用途                         | 生命周期与持久化                                     |
| --------------- | ---------------------------- | ---------------------------------------------------- |
| 引擎 entity ID  | snapshot 引用、编译与运行    | SDK 自动产生；沿用版本化协议，不要求源码填写         |
| 编辑会话 handle | 拖动、选择、撤销、待提交事务 | 编辑会话生成；绑定 source revision，不落入用户 TS    |
| 来源描述        | 把一次操作定位回具体生成位置 | AST 结构、调用上下文和执行记录；可缓存，但缓存可重建 |

来源记录至少区分：定义位置、引用/放置位置、当前函数调用、生成集合中的此次产出、
后续转换，以及最后写入某个属性的位置。使用独立元数据表，不污染用户对象的可枚举属性。

同版本操作用精确 handle。跨版本先做 AST 编辑区间与结构匹配，再结合调用上下文、
输入值、邻接实例、归属关系进行核对。内容 hash、数组下标、文件行号都只能作为证据。
完全重复候选不做自动消歧；在不同文件间移动或大幅重构也不承诺总能恢复旧选择。

一旦保存，修改已经成为普通 TS 表达式或数据，不需要下次启动再通过旧 handle 重放。
可选本地缓存仅保存索引、视图偏好和撤销辅助信息；不能保存唯一的音乐覆盖或随机种子。

## 4. 先决定用户在编辑哪一层

同一个图形对象可能来自定义、放置实例、循环轮次与生成器规则。UI 必须区分这些层次，
但日常操作不弹出一连串确认：编排区拖动/替换默认影响选中的放置实例；编辑规则是单独入口。

| 操作                              | 默认语义                                   | 可选的更大范围                        |
| --------------------------------- | ------------------------------------------ | ------------------------------------- |
| 移动或替换一个 Clip               | 只改变这个放置实例；替换默认保留编排窗口   | 修改所有选中实例或生成规则            |
| 删除一个生成实例                  | 从该生成范围的最终编排中排除该实例         | 缩短生成长度或改变规则                |
| 在实例视图修改共享 Pattern 的音符 | 为该实例派生局部变体，其他引用继续共享     | 明确进入 Pattern 定义视图修改全部引用 |
| 编辑一次循环中的音符              | 只改变该轮次，必要时分裂 Clip              | 修改整个循环的 Pattern                |
| 编辑生成器面板的步长/次数         | 修改该规则，更新它的产出                   | 无需推测为某个实例的例外              |
| 移动到另一条轨道                  | 修改放置归属，按目标 Track 的 Channel 播放 | 保留原声音需另一项显式路由操作        |

实例视图与 Pattern 定义视图用持续可见的范围提示区分；显示受影响的其他引用。
普通拖动允许重叠，不隐式交换或挤开相邻 Clip；吸附只改变目标位置。
替换为更短/更长 Pattern 时，保持窗口与适配新长度应是明确的编排语义。

编辑会话应保留比最终 snapshot 更丰富的中间表示：定义、引用、生成调用、集合转换、
放置和循环轮次组成的来源图。每条命令先作用于这张图的明确层次，再选择源码改写器；
不把所有高阶结构提前压成互不相关的 Note。这是可重建的控制侧模型，不是第二种工程文件。

为现有 chord/arp、Clip 变换及 automation 组合逐步提供“生成与编辑规则”。例如
移调后的单音编辑，要区分修改原音高与在这次调用后增加局部修正；规则同时声明共享范围、
能否拆分和所需前置条件。普通用户函数仍可使用，无法识别时在其输出边界处理，
不要求每个用户为 helper 编写逆函数。已知规则也不能声称能求解任意 map 回调。

## 5. 高阶函数被打破时，源码如何变化

以下示例的普通 TS 和 `track.add(...).at(...)` 沿用现有写法；它们说明输出形式，
不是声称已实现通用重构器。示例假设 4/4、每个 Pattern 两小节，无概率事件。

### 5.1 少量例外：在实例的生成位置表达修改

原代码把 groove 放置在第 1、3、5、7、9、11、13、15 小节：

```ts
Array.from({ length: 8 }, (_, index) => {
  track.add(groove).at({ bar: 1 + index * 2 });
});
```

用户把第 5 小节的实例移动到第 6 小节，把第 7 小节的实例替换成 fill，保存候选为：

```ts
Array.from({ length: 8 }, (_, index) => {
  const bar = 1 + index * 2;
  const pattern = bar === 7 ? fill : groove;
  track.add(pattern).at({ bar: bar === 5 ? 6 : bar });
});
```

这里的 `bar` 是修改前生成位置，表达音乐规则，移动后也不重新寻找“第 5 小节的 Clip”。
下一次编辑已移动实例时更新已有条件，不能反复叠加补丁或靠当前显示顺序定位。
替换仅改 Pattern 引用，保留 groove 的定义和其余放置。变量名冲突由作用域分析消除。

这种输出表示“原规则生成在第 5/7 小节的实例有例外”。若用户以后改变步长，例外是否
仍命中由普通 TS 条件决定；UI 应当反映新结果。不能宣称它还能追踪任意重写前的抽象身份。
仍有未保存图形事务时必须先解决源码版本冲突，不能把旧条件自动套到新生成器。

纯位置不唯一、同一调用生成多个重叠实例时，不生成可能多次命中的条件。可用已有的
领域输入或明确的局部序号表达“第 n 次产出”；序号是可读的规则，不是永久身份。
无法证明只修改目标时，转向局部显式编排或保留未提交编辑，不能扩大修改范围。

### 5.2 例外很多：把这一段编排变成显式数据

反复移动、替换和删除后，条件堆叠可能比数据更难维护。可以转换该生成段：

```ts
const placements = [
  { pattern: groove, bar: 1 },
  { pattern: groove, bar: 3 },
  { pattern: groove, bar: 6 },
  { pattern: fill, bar: 7 },
  { pattern: groove, bar: 9 },
  { pattern: groove, bar: 11 },
  { pattern: groove, bar: 13 },
  { pattern: groove, bar: 15 },
];

for (const { pattern, bar } of placements) {
  track.add(pattern).at({ bar });
}
```

展开的是八个放置关系，不是 groove 的音符、整个歌曲、插件状态或共享函数实现。
用户可以继续手写这个数组，也可以以后自己提取新规则。默认不自动把显式数据重新压缩成
推测出的高阶函数，避免几轮保存后源码在不同风格间跳动。

保留原创建顺序；不能因为时间位置变化自动排序执行语句。未来效果若依赖创建顺序，
这种排序可能改动实体 ID、概率、混音顺序或后续读取行为。

建议初版把“展开为独立编排”做成明确操作，不因固定例外数量阈值静默展开。
UI 可在条件复杂时建议转换，但不会每次编辑都询问。失去对上游生成参数的跟随，
是转换本身的语义，操作前显示范围；普通保存不另设审批步骤。

### 5.3 嵌套生成与共享函数：在调用侧局部展开

同一个 `makeSection(...)` 生成多个段落时，修改其中一段不得直接修改共享函数体。
优先修改该调用的输入；如果是纯函数返回 Note/placement 数据，可在调用侧增加局部转换，
或将这次调用的结果转换为显式数据，其他调用仍使用原函数。

`flatMap` 的一次输入可能产生多项，`filter` 会改变输出序号，`sort` 会改变顺序。
来源关系是多对多的，不能假设“输出 index 就是输入 index”。记录派生链，不通过
全局 snapshot diff 反推输入位置。完全相同音符的最终排序也不能替代来源记录。

若函数直接修改 Project、同时写日志/文件或有闭包副作用，不能把它删除后仅替换为
观察到的音符，也不能重复调用以取得局部结果。此类函数优先考虑受控的 SDK 操作捕获边界，
或先做一次可审查的局部重构；当前无法支持时明确限制该操作，不承诺通用自动展开。

## 6. 推荐的能力层次与备选方案

| 路径                         | 适用场景                             | 主要代价                                           | 建议                             |
| ---------------------------- | ------------------------------------ | -------------------------------------------------- | -------------------------------- |
| 修改唯一字面量/参数          | 直接声明，或明确编辑规则             | 必须分析共享引用、后续赋值与别名                   | 优先                             |
| 调用侧条件或集合转换         | 少数实例例外，纯数据流               | 条件有规则语义，不能保证任意重构后身份不变         | 默认的局部改写                   |
| 局部显式编排/音符数据        | 实例结构已明显偏离生成规则           | 展开范围不再跟随被替换的生成逻辑                   | 明确可选操作                     |
| SDK 捕获生成操作并编辑其结果 | 任意 helper 内调用 SDK，难以源码反演 | 必须定义对象返回值、读取时机、作用域和重复调用语义 | 第二阶段实验                     |
| 全局 ID/下标覆盖文件         | 实现快                               | 脆弱定位、源码语义分散、隐藏状态                   | 不作为默认持久化方案             |
| 完整 snapshot 转 TS          | 脱离原工程的导出                     | 丢失用户抽象，重写面太大                           | 仅显式导出，不用于日常保存       |
| AI 任意改写函数              | 复杂重构辅助                         | 无确定性和语义等价保证                             | 可选提案工具，不进入基础保存路径 |

捕获边界如有必要，应保存为正常 TS 中可读的局部操作，自动生效于 CLI/render 和 GPUI，
不依赖编辑器私有重放。新 helper 的名字和签名暂不确定，不能将本草案的概念当成已有 API。
仅拦截 SDK 创建调用不足以实现通用事务：函数可能立即读取新对象或把它返回给别处，
事后删除/替换会使后续结果与预期不一致。必须证明边界可隔离，否则保留限制。

## 7. 来源分析与可改写边界

在原始 TS 上构建 AST、符号与 imports 索引；sourcemap 用于诊断与 bundle 位置回溯。
临时构建产物可插桩，不将来源标记写回用户 TS。先覆盖 SDK 构造/放置/赋值调用和已知
纯 helper，再覆盖局部 map/flatMap 等；并非解析了 AST 就自动理解所有 JS 运算。

来源追踪必须保持 `this`、参数求值顺序、异常、getter 次数和 async 调用上下文；不能
靠一个全局调用栈处理并发 async factory。插桩开销受预算约束，仅在 Node 控制侧发生。
通过 SDK 边界能知道对象在哪里创建，但不足以知道任意算术值的来源：属性级追踪和受限
静态分析是单独工作。动态读取、未执行分支和包内部实现不能伪装成已分析的可编辑源码。

每个可编辑目标携带明确能力：直接改值、改生成输入、局部例外、可展开、当前不可改写。
能力按这次执行和选定范围计算；同一个文件中可混合支持，不要求整份工程符合新 DSL。
共享常量或 alias 默认不直接改定义；对局部编辑优先在使用位置表达新值。

## 8. 草稿、保存和外部代码修改

1. GPUI 发送语义命令，带 source revision、session handle、作用范围和旧值前置条件。
2. Node 编辑会话在内存中构建最小源码补丁；已有 AST 文本区间做保留格式的修改，
   新生成区域按项目风格打印，不把整个源文件重新格式化。
3. 从一致的源码草稿构建并执行，校验结构，再由 Rust 在控制线程验证候选图。
   检查实际结果是否等于预期编辑，确认未授权的编排/引用没有改变；不声称能证明
   任意 TS 的未来行为等价。外部 I/O 与未固定随机输入必须记录依赖或判为不可验证。
4. 候选接受后更新草稿预览；一段拖动是一条撤销事务。参数试听可以节流发送控制命令，
   结构变化走候选图；不能每个鼠标事件都执行整份 TS。
5. 保存前核对所有读取源文件的版本与内容。语法不冲突仍不等于音乐语义不冲突；
   外部修改影响目标或生成范围时重新验证，歧义时保留草稿并显示冲突。
6. 单文件使用同目录临时文件、fsync 和 rename 发布。首个原型限定单源文件事务；
   跨文件保存以后需要事务日志、恢复与会话协调，多个 rename 不构成文件系统整体原子性。
   无法承诺非协作编辑器在检查和 rename 间写入时绝对无竞争，需要复核与恢复设计。

源码 revision、草稿 revision 与音乐 snapshot revision 分开。只改注释、变量名或函数
位置也必须更新来源映射，不能因 snapshot hash 不变跳过；编辑请求另带 request ID，
不能复用当前“收到任意应答就释放唯一 in-flight frame”的逻辑，也不能丢弃中间编辑命令。
watch 根据版本/内容识别自身保存，仍处理真正的外部修改；不能用固定时间窗口屏蔽事件。

Undo/redo 保存源码事务与语义操作。外部修改后只撤销仍能安全重放的事务，不用整文件
旧副本覆盖用户的新代码。失败时最后合法播放图继续工作，草稿与保存状态明确区分。
再次执行用于校验不是副作用沙箱，不能以子进程隔离为理由认定任意用户函数可安全重复调用。

## 9. 循环轮次、概率与时序是单独的正确性门槛

`.loop(8)` 是一个 Clip 的八轮播放，不是八个已经存在的 Clip。移动第四轮时，编辑目标
至少包含 `(clip handle, iteration)`；修改其某个音符还需 Note 来源。普通实例 ID 不够。

可考虑分为前段循环、独立轮次、后段循环。必须保持原时钟、Pattern offset、exclusive end、
截断、transpose、velocityScale、概率和已绑定 automation 的语义。跨界长音符的行为
须遵循真实 scheduler，不凭图形外观猜测；更不能直接用小节数代替精确 rational beat。
Track 独立 tempo、变速和变拍号要求先确定编辑坐标域，再做统一换算。

当前 ID/轮次/Note ordinal 参与概率采样，即使音高时间相同，分裂后的播放也可能不同。
新增实例还可能推进全局 ID 序列，影响后面没有编辑的 Clip。内容一致比较不能忽略这些字段。

因此无损循环拆分在以下问题解决前不宣称支持：

- 能否在受限重构中保留创建顺序、旧运行身份和原始随机事件寻址？这只覆盖部分情况。
- 若新增自动派生的随机来源/轮次偏移语义，它必须版本化，在普通 TS 执行和重新打开时
  可重建，不能把唯一依据藏进 `.oxitone` 缓存，也不能变相要求源码加入 opaque ID。
- 若需要用户选择“固定当前生成结果”，应明确冻结的是哪些概率/生成行为；不能静默
  烘焙一次播放，把以后循环应变化的音乐改成固定音符。

第一阶段优先验证无概率事件的独立放置与纯 Note 数据变换，循环拆分另设验收门槛。
概率/随机算法变化同步更新 02/03/06/07 的相关契约与 golden vectors，保留旧算法兼容。

## 10. 原型顺序与讨论问题

先做源码层原型，使用现有歌曲的缩小 fixture，不先投入整套 GPUI 拖动 UI：

1. 无手写 ID 的八次 Pattern 放置：移动一次、替换一次、删除一次；重复编辑已移动实例。
2. chord/arp 单音编辑及其嵌套组合；同一个纯 helper 调用两次、嵌套 flatMap、共享 Pattern：
   只改变选定输出/调用/实例；arp 删除单步保持后续时序与力度曲线结果。
3. 从少量例外转换为显式 placements；源码注释保留，无操作保存字节不变。
4. 删除缓存并在新进程执行已保存 TS：结果与已接受草稿一致；多轮保存不堆叠补丁。
5. 外部重命名、插入、调序和完全重复实例：能唯一定位才重放，否则保留冲突草稿。
6. 独立验证循环分裂、chance/概率、跨界音符、Track tempo 与导出一致性，再开放对应能力。
7. 按逐项审计验证 automation 区间编辑、Slicer/钢琴分区与配置绑定，不能用编排原型代替验收。
8. 插件管理器与真实外部音源/效果器参与添加、局部编辑、保存回读、版本/依赖与面板回退验收。

验证同时比较原始源码、候选源码、预期语义差异和未编辑部分。基准分别测 AST 索引、
来源记录大小、单次编辑重建与 GPUI 响应；不把 Node 编辑耗时混作 callback 性能。
音频验证只用离线 PCM/WAV、MIDI 和 simulated sink，绝不打开系统输出。

建议优先讨论三个产品选择：

- 是否接受“少量例外保存为局部条件，复杂后显式展开这一段”的默认策略？它保留高阶
  函数，但不会承诺所有图形操作都能永远维持原函数的简洁形式。
- 对共享 Pattern，实例视图默认派生变体、定义视图修改所有引用，是否符合预期？
- 对不透明且有副作用的生成函数，先限制无法证明的结构编辑，还是投入新的 SDK
  生成操作边界？建议先用现有歌曲验证前两类写回，依据实际覆盖率决定新 API。

本次仅落讨论草案。实施前再更新正式架构/预览/插件 UI/格式契约，定义版本化编辑协议，
保持 Rust 独占音频执行，所有 AST、文件与事务工作留在 Node/UI 控制侧。
